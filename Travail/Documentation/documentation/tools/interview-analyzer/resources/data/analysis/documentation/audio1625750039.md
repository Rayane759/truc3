## 1️⃣ Synthèse – Points positifs & irritants / incohérences (protopersona)

| **Catégorie** | **Ce qui fonctionne / points positifs** | **Ce qui pose problème / irritants** |
|---------------|----------------------------------------|--------------------------------------|
| **Accès & découverte** | - Le nouveau site de présentation des catalogues a été jugé « intéressant » et aide les nouveaux arrivants à comprendre les projets. <br>- Les tickets sont centralisés (GitLab backlog, Tulip) et visibles par l’équipe. | - La documentation d’accès aux différents catalogues reste fragmentée : l’interviewé ne sait pas toujours s’il a les droits ou où trouver les informations. <br>- Le *setup* du poste (installations, variables d’environnement, proxy) est peu documenté et difficile à reproduire. |

| **Communication & support** | - Les collègues (Colin, David, Maxence, Antoine) sont réactifs et partagent des canaux (IDDA, Kube, etc.). <br>- La communauté interne partage des bonnes pratiques (ex. : gestion des CVE, usage de Sonar). | - Les canaux de communication (Slack, groupes) sont nombreux et peu filtrés : l’interviewé ne sait pas toujours quels flux consulter quotidiennement. <br>- Le rôle du **DOT** (Direction Opérationnelle des Technologies) est flou : il possède les catalogues mais ne les « gère » pas clairement, ce qui crée des frictions de responsabilité. |

### 2.3 Points forts relevés  

* **Bonne maîtrise technique** – le participant se sent à l’aise avec la stack et les outils CI/CD.  
* **Utilisation de l’IA** – perçue comme un gain de productivité.  
* **Autonomie** – il peut réparer un pipeline sans escalade.  
* **Collaboration** – collègues (Colin, David, Maxence, Antoine) apportent un support rapide.  

### 2.4 Irritants & incohérences  

| **Thème** | **Exemple d’irritant** |
|-----------|------------------------|
| **Documentation d’onboarding** | Le *setup* du poste (proxy, variables d’environnement) est mal documenté → perte de temps. |
| **Multiplicité des plateformes** | Catalogues dispersés (GitLab, URL directes, DPII Planet) avec sémantiques différentes. |
| **Standardisation** | Absence de ligne directrice macro : chaque équipe suit ses propres patterns (ex. : tags, Cypress, version Spring). |
| **Canaux de communication** | Trop de groupes Slack/IDDA, difficile de savoir quels flux consulter quotidiennement. |
| **Processus de promotion d’image** | Blocage sur les tokens/usernames lors du push d’image Docker, pas de documentation claire. |
| **Gestion des secrets** | Utilisation de Volt & Kicklock, mais la mise en place reste « très manuelle ». |
| **Responsabilité du DOT** | Le rôle du DOT est flou : il possède les catalogues mais ne les « gère » pas clairement, créant des ambiguïtés de responsabilité. |
| **Manque de daily** | Absence de daily stand‑up → visibilité réduite sur les blocages urgents. |
| **Cypress vs VTest** | Le métacomposant ne propose pas d’image Docker Cypress prête à l’emploi, obligeant à créer un CI dédié. |

### 2.5 Besoin d’une ligne directrice / gouvernance  

* Le participant évoque plusieurs fois le souhait d’une **« ligne directrice »** (standardisation macro) qui couvrirait :  
  - Choix de versions (ex. : migration Spring Boot 3 → 4).  
  - Patterns de CI/CD (tags, métacomposants, Cypress).  
  - Documentation d’onboarding (setup, variables, secrets).  
* Il estime que cela faciliterait la prise en main d’un projet étranger et réduirait le « bruit » dans les canaux de communication.  

### 2.6 Observations sur le **CICD**  

* Les pipelines sont globalement similaires (lint → security → build → sonar → publish).  
* Les étapes de **check alignment** (alignement des branches) sont perçues comme peu répandues.  
* Le participant ne remarque pas de **guidelines** formelles, le tout repose sur le « hasard » ou les bonnes pratiques partagées informellement.  

### 2.7 Enjeux de **serverless**  

* Le développeur remarque que l’équipe utilise majoritairement des VMs/Kubes et très peu de fonctions **serverless** (ex. : AWS Lambda).  
* Il s’interroge sur les gains économiques potentiels d’une adoption plus large du serverless.  

### 2.8 Conclusion de l’interview  

* Le participant se montre **enthousiaste** quant à la technologie et aux outils, mais souligne **une forte nécessité d’harmonisation** (documentation, standards, gouvernance).  
* Il est **prêt à contribuer** à l’amélioration de la documentation et à partager ses bonnes pratiques, à condition d’avoir un cadre clair.

## 3️⃣ Autres éléments (sans préconisations)

* **Temps d’onboarding** – Le participant estime qu’une mise en place d’un nouvel environnement (ex. : dev 2 Gardien) prend **moins d’une demi‑journée** lorsqu’il connaît déjà la chaîne.  
* **Utilisation de la documentation** – La documentation actuelle (ex. : guide de mise en place de Kicklock) est jugée suffisante lorsqu’elle existe, mais son absence est un frein.  
* **Culture DevOps** – Le développeur adhère à la philosophie *« you build it, you run it »* mais reconnaît que certaines tâches (ex. : configuration du Kube) nécessitent l’intervention d’équipes spécialisées.  
* **Gestion des versions** – La migration de Spring Boot 3 → 4 est perçue comme une contrainte imposée par la direction, sans accompagnement centralisé.  
* **Rôle du DOT** – Le DOT centralise les catalogues mais n’est pas clairement identifié comme propriétaire de la gouvernance, ce qui crée des ambiguïtés de responsabilité.
