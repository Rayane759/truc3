## 2️⃣ CR des échanges (extraits & thèmes)

### 2.1 Contexte professionnel
- **Rôle** : développeur Java/React, intervenant sur la plateforme et le déploiement (dev‑ops).  
- **Ancienneté** : 15 ans chez l’INSEE, a vu plusieurs évolutions de la stack (Spring Boot, React, Docker, GitOps).  
- **Projet actuel** : « Agathe » (stack : PostgreSQL, Java, React, Spring Boot).  

### 2.2 Utilisation des outils
- **Stack quotidienne** : Java, SQL, Spring Boot, React, Docker, Argo CD, Argowalkflow, Grafana/Loki.  
- **Déploiement** : plusieurs fois par semaine, via pipelines CI/CD automatisés.  
- **Observabilité** : Grafana/Loki jugés fonctionnels mais peu conviviaux, surtout pour le suivi des batchs.  

### 2.3 Points forts identifiés
- **Fiabilité du pipeline CI/CD** : le participant ne rencontre pas de blocage technique majeur lorsqu’il modifie ou ajoute des étapes.  
- **Standardisation des outils** : Argo CD et le modèle GitOps sont perçus comme « parfaitement » intégrés.  
- **Formation interne** : il existe des sessions de formation sur la plateforme engineering, appréciées lorsqu’elles sont bien ciblées.  

### 2.4 Irritants majeurs
1. **Fragmentation des catalogues**  
   - Accès via plusieurs plateformes (GitLab, URL directes, DPII Planet) → perte de temps.  
2. **Documentation insuffisante**  
   - Guides trop génériques, manque de spécificités INSEE, difficulté à retrouver les informations d’onboarding.  
3. **Multiplicité des canaux de communication**  
   - Slack, mails, tickets, chats « INSEE TOTO » → fatigue, hésitation à poser des questions.  
4. **Observabilité « by‑default »**  
   - Chaque équipe doit créer ses propres dashboards ; les outils existants (Grafana/Loki) ne sont pas assez ergonomiques pour les besoins batch.  
5. **Gestion du changement**  
   - Migration d’outils (ex. : Minayo) perçue comme « ras‑le‑bol » lorsqu’elle n’est pas accompagnée d’une formation claire.  

### 2.5 Insights sur la collaboration dev‑ops
- Le développeur estime que la **collaboration** est bonne, mais il manque un **point d’entrée unique** pour les questions production.  
- Il souhaite que les **Ops** partagent davantage les connaissances (ex. : « qui contacter », « quels tickets ») afin d’éviter les allers‑retours.  

### 2.6 Suggestions exprimées (sans préconisation)
- **Centraliser l’information** : une page d’actualités unique regroupant nouveautés, incidents, changements de version.  
- **Dashboard batch** : un tableau de bord pré‑configuré pour le suivi fin des logs par batch, sans devoir connaître le nom du pod.  
- **Documentation « INSEE‑specific »** : inclure les mots‑clés internes, les responsabilités, les procédures d’onboarding.  
- **Point de contact unique** : un canal ou une équipe « porte‑d’entrée » qui redirige les devs vers les bonnes personnes.

## 3️⃣ Autres éléments relevés (sans recommandations)

- **Maturité des outils** : certains outils proposés par l’équipe « Kube » ne sont pas encore matures (manque de documentation, licences expirées, CVE).  
- **Gestion des licences** : le cas de la console « Mignot » retirée pour cause de licence et de vulnérabilités.  
- **Test containers** : le participant mentionne un projet interne de « test‑container » (Docker‑in‑Docker) qui devrait être généralisé.  
- **Observabilité future** : anticipation d’une solution d’observabilité unifiée (remplacement de Grafana/Loki).  
- **Réticence à la duplication** : le développeur préfère éviter de dupliquer les efforts (ex. : créer un nouveau pipeline lorsqu’un existant suffit).  
- **Culture du « shift‑left »** : il souligne l’importance d’impliquer les devs dès la conception pour éviter les frictions ultérieures.  
- **Gestion des secrets** : besoin d’un accès en lecture aux secrets en production sans pouvoir les modifier, afin de faciliter le debugging.
