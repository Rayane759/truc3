# Compte‑rendu d’interview – Mise en place du **Platform‑Engineering**  
*(interview anonyme, senior développeur / DevOps, ~15 ans d’expérience, projet “Agathe”)*
  

---  

## 1️⃣ Contexte & missions quotidiennes  

| Élément | Description |
|---|---|
| **Rôle principal** | Développeur full‑stack (Java / Spring Boot, React) avec une forte composante **DevOps / plateforme** (mise en place, déploiement, support). |
| **Projet phare** | “Agathe” (déploiement d’une application Java + React, base PostgreSQL). |
| **Activités récurrentes** | • Analyse des user‑stories, rédaction de spécifications fonctionnelles (FHPL). <br>• Développement, tests unitaires et d’intégration. <br>• Construction et exécution de pipelines CI/CD (build, test, lint, déploiement). <br>• Déploiement en production (souvent plusieurs fois par semaine). <br>• Support aux équipes DDC (déploiement, incidents). <br>• Participation à la maintenance de la plateforme interne (Kube / KubeApp). |
| **Temps passé** | Environ 70 % sur le projet Agathe, 30 % sur le support et l’évolution de la plateforme. |
| **Vision du DevOps** | Collaboration étroite : *“you build it, you run it”* – les développeurs doivent connaître le cycle complet, mais ils souhaitent un point d’entrée unique pour les questions opérationnelles. |

## 3️⃣ Irritants & points de friction  

| Domaine | Irritant / Friction |
|---|---|
| **Documentation** | - Documentation dispersée, difficile à retrouver. <br>- Manque de versionning clair, de responsabilité et de liens vers les docs officielles. <br>- Onboarding peu fluide (trouver le “setup initial”, les bonnes pratiques). |
| **Outils immatures** | - Certains outils internes (Kube, KubeApp) manquent de maturité, de guides d’utilisation et de support. <br>- Licences expirées (ex. Mini‑Console) créent des vulnérabilités (CVE). |
| **Observabilité** | - Grafana/Loki jugés peu conviviaux, besoin d’une vue unifiée des logs batch. <br>- Absence d’observabilité “by‑default” → chaque équipe doit la mettre en place. |
| **Communication** | - Multiplicité des canaux (Slack, mails, chats) → fatigue et perte d’information. <br>- Pas de point d’entrée unique pour les questions production / plateforme. |
| **Processus de migration / évolution** | - Changements de stack (ex. remplacement de Minio) peu communiqués, pas de plan de migration clair. <br>- Les équipes doivent parfois “deviner” qui contacter. |
| **Temps de pipeline** | - Pipelines parfois longs (5‑10 min) → perte de productivité lors de petits changements. |
| **Responsabilité & ownership** | - Ambiguïté sur qui doit intervenir (dev vs ops) pour les tâches de run‑time (ex. mise à jour de version, sauvegarde). |
| **Accès production** | - Accès limité aux consoles de prod, besoin de “push‑and‑prime” local pour tester rapidement. |
| **Formation** | - Besoin d’un accompagnement structuré (formation, tutoriels) pour les nouveaux outils et pratiques. |

## 4️⃣ Besoins exprimés (ou implicites)  

| Besoin | Détails |
|---|---|
| **Documentation centralisée & searchable** | - Un portail unique contenant guides d’onboarding, procédures, responsabilités, mots‑clés. <br>- Versionnée, maintenue à jour, avec liens vers les docs officielles. |
| **Observabilité prête à l’emploi** | - Dashboard unifié (logs, métriques, suivi batch) accessible en lecture simple. <br>- Alertes configurables, visibilité sur les pipelines. |
| **Support & point d’entrée unique** | - Canal ou équipe “Platform‑Support” qui redirige les requêtes (dev ↔ ops) sans que chaque développeur doive deviner le contact. |
| **Formation & accompagnement** | - Parcours de formation (vidéos, labs) pour les outils Kube, Argo, test‑containers, CI/CD. <br>- Sessions de “pair‑programming” ou de coaching lors de l’onboarding. |
| **Self‑service fiable** | - Outils de déploiement (Argo CD, KubeCTL) bien documentés, avec des templates “nominal” pour chaque type d’application (Java, batch, etc.). |
| **Gestion de la migration** | - Processus standardisé pour les changements de stack (ex. remplacement de Minio) avec communication anticipée. |
| **Réduction du temps de pipeline** | - Optimisation des étapes, caching, parallélisation, afin de passer sous les 5 min pour les petits changements. |
| **Accès local à la prod** | - Environnements “local‑clone” de la prod (Docker‑in‑Docker) pour tester rapidement sans attendre le pipeline complet. |
| **Clarté des responsabilités** | - Matrice RACI (qui fait quoi) visible dans la documentation et dans les tickets. |
| **Sécurité & conformité** | - Gestion centralisée des secrets, licences à jour, auditabilité des changements. |

## 5️⃣ Insights clés pour le **Platform‑Engineering**  

| Insight | Implication pour la plateforme |
|---|---|
| **Documentation est le nerf de la mise en œuvre** | Une plateforme qui ne fournit pas de documentation claire crée des frictions majeures (onboarding, support, adoption). |
| **Observabilité doit être intégrée, pas ajoutée** | Les équipes attendent des logs et métriques prêts à l’emploi ; le “build‑it‑you‑run‑it” ne fonctionne que si l’observabilité est baked‑in. |
| **Un point d’entrée unique réduit le bruit** | Un canal ou une équipe de “Platform‑Support” qui centralise les questions et les redirige améliore la productivité et la satisfaction. |
| **Self‑service doit être accompagné** | Les outils (Argo CD, KubeCTL, test‑containers) sont puissants mais nécessitent des guides, des templates et du coaching pour être adoptés. |
| **Cohérence des pipelines** | La convergence des pipelines est perçue comme bénéfique ; standardiser les étapes et les templates évite la dette technique et les variations inutiles. |
| **Temps de feedback court** | Réduire la latence des pipelines (5‑10 min → < 5 min) est crucial pour le flow quotidien des développeurs. |
| **Gestion des migrations comme service** | Les changements de stack doivent être traités comme un service (plan, communication, scripts de migration) pour éviter les blocages. |
| **Responsabilité claire** | Une matrice de responsabilités visible (qui fait le run, qui fait le build, qui gère les secrets) évite les confusions et les tickets redondants. |
| **Formation continue** | La plateforme doit proposer des ressources d’apprentissage (labs, tutoriels) pour garder les équipes à jour sur les outils. |
| **Sécurité proactive** | Gestion centralisée des licences, des CVE et des secrets est attendue ; les outils doivent être maintenus à jour. |

## 6️⃣ Autres éléments observés  

* **Culture de “push‑and‑prime”** – Les développeurs souhaitent pouvoir pousser du code et le tester immédiatement, sans passer par un long pipeline.  
* **Variabilité des outils selon les projets** – Certains projets utilisent des “technos exotiques” (ex. VIT, Minio) qui compliquent la standardisation.  
* **Importance du “batch”** – Une partie importante du travail repose sur des traitements batch ; la visibilité et la gestion de ces jobs sont critiques.  
* **Sensibilité à la charge cognitive** – La multiplicité des canaux de communication et le manque de centralisation augmentent la fatigue et le risque d’erreurs.  
* **Attente d’une plateforme “autonome mais guidée”** – Les équipes veulent être autonomes, mais avec un cadre clair, des templates et un support réactif.
