## 3️⃣ Irritants & points de friction
| Type | Description détaillée |
|------|-----------------------|
| **Découverte d’outils** | Multiplicité d’outils (Rundeck, Sonar, Majiba, Elastic, etc.) → difficulté à identifier rapidement le bon outil et à comprendre son périmètre. |
| **Documentation** | Documentation fragmentée, parfois absente ou difficile à localiser (ex. “notice d’accompagnement” manquante). |
| **Onboarding** | Courbe d’apprentissage élevée : besoin de passer par plusieurs démos, salons de discussion, et “chat” pour obtenir une réponse rapide. |
| **Gestion des accès** | SSO sur certains outils (Rundeck) perçu comme peu intuitif ; manque de visibilité sur les droits et les secrets (Vault, KeyCloack). |
| **Processus de déploiement** | Commit de jobs Rundeck peu clair, pas d’indicateur de succès visible. <br>Modification directe du repo de contrôle (contournement du CD) parfois nécessaire, ce qui crée des incohérences. |
| **Visibilité des ressources** | Absence de suivi en temps réel de la consommation (ex. bases de données volumineuses) → crainte de “gaspiller” des ressources lors de créations d’environnements. |
| **Communication inter‑équipes** | Trop de canaux (démo, chat, intranet) → perte d’information, besoin de “savoir dans quel salon poster”. |
| **Responsabilité du déploiement** | Le passage d’une VM classique à un environnement Kubernetes (Kube) représente un **coût d’entrée** important, avec peu de support dédié. |
| **Support de niveau 1,5** | Dépendance au chef de domaine pour les incidents de production ; manque d’autonomie sur certains sujets (ex. tags de déploiement en prod). |

## 4️⃣ Besoins exprimés (ou implicites)
| Besoin | Pourquoi il apparaît |
|--------|----------------------|
| **Vue d’ensemble unifiée** | Un tableau de bord ou un catalogue centralisé listant tous les outils, leurs usages et les contacts associés. |
| **Documentation claire & centralisée** | Guides “how‑to”, bonnes pratiques et procédures d’onboarding accessibles depuis un point unique. |
| **Automatisation du provisioning** | Outil permettant de créer un environnement complet (VM, DB, jobs batch) à partir de templates, sans passer serveur par serveur. |
| **Gestion transparente des ressources** | Monitoring en temps réel de l’usage des ressources (CPU, RAM, stockage DB) avec alertes et capacité de libérer automatiquement les ressources inutilisées. |
| **Amélioration du SSO / accès** | Authentification unique et fluide sur tous les outils (Rundeck, Vault, etc.) avec gestion fine des droits. |
| **Support réactif & self‑service** | Possibilité de résoudre les incidents mineurs sans passer systématiquement par le chef de domaine (ex. via chat‑bot ou FAQ enrichie). |
| **Standardisation des pipelines** | Uniformisation des pipelines CI/CD (tags, branches) et visibilité sur les étapes de build, test, déploiement. |
| **Formation / montée en compétences** | Sessions de formation ciblées (ex. sur Kubernetes, CI/CD) pour réduire le temps d’onboarding. |
| **Gestion du changement** | Processus clair pour les migrations (ex. passage à la “plichière 4”, adoption de Kube) avec documentation des impacts. |

## 5️⃣ Insights clés pour le **Platform‑Engineering**
| Insight | Implication pour le Platform‑Engineering |
|---------|------------------------------------------|
| **Complexité fragmentée** – La multiplicité d’outils crée une surcharge cognitive. → Un **Platform‑Engineering** doit proposer une **plateforme unifiée** (catalogue d’outils, UI centralisée) qui masque la complexité sous‑jacente. |
| **Onboarding difficile** – Le manque de documentation et de visibilité ralentit la prise de fonction. → **Documentation as Code** et **portail d’onboarding** (guides, vidéos, sandbox) sont essentiels. |
| **Provisioning manuel** – La création d’environnements reste très manuelle (jobs, scripts). → Un **self‑service provisioning** (templates IaC, pipelines automatisés) permettrait de réduire le temps de mise à disposition et le risque d’erreur. |
| **Visibilité des ressources** – Crainte de sur‑consommation sans suivi. → Intégrer un **observability layer** (monitoring des quotas, alertes) dans la plateforme. |
| **Gestion des accès** – SSO et droits sont sources de friction. → Centraliser l’**IAM** (Vault/KeyClock) et offrir un **single sign‑on** cohérent. |
| **Support réactif** – Dépendance au chef de domaine pour les incidents. → Mettre en place un **self‑service support** (chat‑bot, runbooks) et des **run‑books automatisés** pour les incidents courants. |
| **Standardisation des pipelines** – Les pipelines varient mais tendent vers l’uniformité. → Fournir des **templates CI/CD** pré‑configurés et un **catalogue de pipelines** réutilisables. |
| **Transition vers Kubernetes** – Le passage à Kube est perçu comme un gros obstacle. → Créer des **kits de migration** (helm charts, scripts de conversion) et un **support dédié** pendant la phase de transition. |
| **Culture DevOps** – Le développeur se sent déjà “DevOps” mais manque d’outils fiables. → Le **Platform‑Engineering** doit renforcer la **culture de responsabilité partagée** en offrant des outils fiables, documentés et faciles à adopter. |

---

## 6️⃣ Autres éléments observés
- **Rôle hybride** : le développeur combine fonctions de **développeur**, **analyste métier** et **formateur**, ce qui augmente la charge cognitive.
- **Fréquence de déploiement** : un seul déploiement mensuel indique un **pipeline de release** assez lent ; opportunité d’accélérer le cycle via le Platform‑Engineering.
- **Communication** : l’usage de **Tchap** est perçu comme plus rapide que la lecture de documentation, soulignant le besoin d’un **canal de réponse instantanée** (ex. bot Slack/Teams).  
- **Évolution de la stack** : migration progressive vers des technologies plus récentes (Kubernetes, Java 17) mais sans accompagnement structuré.
