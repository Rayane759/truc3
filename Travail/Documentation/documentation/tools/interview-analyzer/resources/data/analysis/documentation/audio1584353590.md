## 1️⃣ Synthèse – Points positifs / Irritants & incohérences (protopersona)

| **Catégorie** | **Ce qui fonctionne / points positifs** | **Irritants / freins** | **Insights clés** |
|---|---|---|---|
| **Organisation du travail** | - Travail partagé entre IHM et batch, bonne répartition des affinités. <br>- Accès à des outils « Protect DevOps », Grafana, Argos, Rendeck, Magiba, etc. | - Multiplicité d’outils (GitLab, VM, Kube, Magiba, Rendeck…) → perte de temps à chercher le bon. <br>- Absence de documentation centralisée (pas de “step‑by‑step” pour créer / supprimer une VM). | *Le besoin d’un point d’entrée unique (catalogue, hub) où chaque service/outil est répertorié et documenté.* |
| **Documentation & recherche d’information** | - La doc interne du « tube » (connaissance du dépôt) est utilisée quand elle est connue. <br>- Les canaux de chat (Slack/Teams) permettent de suivre les incidents. | - Documentation dispersée sur plusieurs GitLab, PDF, intranet, pas de moteur de recherche global. <br>- Pas de versionnage clair des procédures (ex. : création VM, mise à jour sécurité). | *Un moteur de recherche unifié et une taxonomy claire des documents sont attendus.* |
| **Processus de mise en production** | - Déploiement manuel fonctionnel (2 déploiements / semaine). <br>- Pipeline CI/CD existant (vert = OK, rouge = problème). | - Pas de pipeline automatisé pour l’IHM (déploiement encore manuel). <br>- Relances manuelles sur Kube en cas de plantage → dépendance à la disponibilité d’un collègue. <br>- Manque de visibilité sur les étapes du pipeline (boîte noire). | *Automatisation + visibilité (logs, étapes) pour réduire la dépendance humaine.* |
| **Gestion des environnements (VM vs Kube)** | - Confort avec les VM (procédures connues). | - Connaissance limitée du fonctionnement de Kube → difficulté à diagnostiquer / réparer. <br>- Outils plus lents (ex. : HyperX) découragent l’usage. | *Uniformiser les environnements ou fournir des guides spécifiques à chaque plateforme.* |
| **Responsabilités & gouvernance** | - Collaboration avec les équipes “Prod” (support de premier niveau, réponses rapides). | - Rôles et responsabilités flous (ex. : qui doit intervenir sur le passage Nginx → trafic). <br>- Absence de contrat de service ou de “SLA” interne. | *Clarifier le “who does what” via un contrat de service ou un tableau de responsabilités.* |
| **Veille & adoption d’outils** | - L’architecte envoie des newsletters sur les nouveautés. | - Information parfois perdue (messages noyés dans les fils). <br>- Pas de canal centralisé de diffusion des nouveautés. | *Un canal dédié (ex. : newsletter, tableau d’affichage) pour les nouveautés et les incidents.* |
| **Valeur perçue du travail** | - Sentiment d’accomplir des tâches opérationnelles (maintenance, relance). | - Impression de “ne pas créer de valeur” lorsqu’on passe la journée à faire du “ops” (ex. : relance manuelle, mise à jour). | *Faire ressortir la contribution métier (ex. : impact sur la disponibilité des données) pour augmenter la motivation.* |

## 2️⃣ CR détaillé des échanges  

### 2.1 Contexte professionnel & quotidien
* **Poste** : développeuse depuis 2021 (SNDI Orléans).  
* **Équipe** : 2 développeuses sur le produit « Donnée de Caisse ». Répartition : IHM vs batch.  
* **Technos** : Java, JavaScript (pas de React), IntelliJ, VS Code (GitOps), Magiba (déploiement manuel), Grafana, Argos, Rendeck, HyperX (outil lent).  
* **Environnements** : VM (legacy) et Kube (nouveau). Le batch a migré sur Kube, l’IHM reste sur VM.  

### 2.2 Activités récurrentes
| **Tâche** | **Fréquence / Durée** | **Observations** |
|---|---|---|
| Vérif. matinale des jobs nocturnes (chargements, alertes) | ~1 h | Utilise “Grimpanin” pour contrôler les fichiers reçus. |
| Gestion des incidents (re‑lancement manuel, relance à 22 h) | Variable, dépend des plantages | Si la collègue n’est pas disponible, le problème persiste jusqu’au matin. |
| Maintenance VM (déplacement DC2 → DC1) | Occasionnelle | Opération manuelle, nécessite des notes personnelles. |
| Déploiement (manuel) | 2 fois / semaine | Pas de pipeline automatisé pour l’IHM. |
| Développement (features, corrections) | 30 % du temps (ratio 70 % prod / 30 % dev) | Charge de travail élevée sur la partie opérationnelle. |
| Gestion des tickets / suivi des évolutions | Quotidien | Utilise un board (ex. : Valérie) pour les tâches. |

### 2.3 Outils & plateformes
| **Outil** | **Usage** | **Points forts** | **Points faibles** |
|---|---|---|---|
| **IntelliJ / VS Code** | Développement Java, GitOps | Familiarité, ergonomie | Aucun problème majeur |
| **Magiba** | Déploiement manuel (VM) | Fonctionne, mais manuel | Pas d’automatisation, risque d’erreur |
| **Grafana / Argos** | Monitoring & workflow | Utilisé quotidiennement | Aucun problème majeur |
| **Rendeck DevOps** | Gestion de VM (création / suppression) | Permet de créer des VM | Documentation absente, notes perso nécessaires |
| **HyperX** | Accès à certains services | Contient des infos utiles | Lenteur → abandon progressif |
| **GitLab** | Repos de code, docs (fragmentées) | Centralisation du code | Multiples dépôts, recherche difficile |
| **PDF “roue de la prod”** | Référence ponctuelle | Disponible offline | Pas à jour, pas de recherche |

### 2.4 Documentation & recherche d’information
* **Sources utilisées** : doc du “tube” (dépot connu), PDF “roue de la prod”, chats d’équipe, newsletters de l’architecte.  
* **Problèmes** :  
  * Pas de moteur de recherche global → perte de temps.  
  * Pas de “step‑by‑step” pour les actions récurrentes (ex. : création VM, mise à jour sécurité).  
  * Documentation parfois “cachée” dans les paquets d’outils (ex. : Rendeck).  

### 2.5 Responsabilités & gouvernance
* **Clarté des rôles** : parfois floue (ex. : qui doit intervenir sur le passage Nginx → trafic).  
* **Support** : premier niveau – contacte les équipes “Kube IDDA PDD”, réponses rapides.  
* **Contrat de service** : aucune formalisation écrite, dépendance à la bonne volonté.  

### 2.6 Processus de mise en production (CI/CD)
* **Pipeline existant** : affichage couleur (vert = OK, rouge = problème).  
* **Utilisation** : pas de création de pipeline de A à Z, seulement des ajouts ponctuels.  
* **Points de friction** :  
  * Boîte noire – l’opératrice ne voit pas les étapes détaillées.  
  * Les CVE bloquent le pipeline (rouge) → besoin d’intervention manuelle.  
  * Déploiement IHM encore manuel, ralentissant le rythme.  

### 2.7 Veille technologique & adoption d’outils
* **Canaux** : newsletters de l’architecte, chat d’équipe, échanges informels.  
* **Limites** : messages noyés, pas de suivi centralisé, perte d’information.  

### 2.8 Perception de la valeur du travail
* **Sentiment** : “je ne crée pas de valeur” lorsqu’elle passe la journée à relancer des jobs ou à faire des tâches “ops”.  
* **Motivation** : plus d’automatisation et de visibilité sur l’impact métier améliorerait la satisfaction.  

### 2.9 Idées de “monde parfait”
* **Interface unique** : un bouton qui génère automatiquement tout le nécessaire (YAML, scripts) tout en affichant les étapes de façon pédagogique.  
* **Documentation vivante** : guide pas à pas, recherche instantanée, mise à jour collaborative.  
* **Clarification des responsabilités** : tableau de qui fait quoi, SLA interne.

## 3️⃣ Autres éléments pertinents (sans préconisations)

* **Charge d’onboarding** : le passage à un nouveau poste nécessite de recopier des listes d’outils et de configurations – processus jugé lourd.  
* **Formation** : l’interviewée a ressenti une surcharge de formation à l’arrivée, surtout sur les outils de la “prod”.  
* **Transversalité** : la difficulté principale lorsqu’on change d’équipe est la découverte de nouvelles technologies non utilisées dans son périmètre actuel.  
* **Temps de résolution** : les incidents critiques (ex. : plantage Kube à 22 h) sont résolus rapidement si la bonne personne est disponible, sinon le délai s’allonge.  
* **Culture “you build it, you run it”** : l’interviewée se sent partiellement en accord, mais estime que le “run” reste trop dépendant d’interventions manuelles et de connaissances tacites.  
* **Utilisation de l’IA** : copie‑coller de parties de pipeline entre projets est courante, l’IA n’est pas encore perçue comme un frein.  
* **Communication** : les canaux de chat sont utiles pour les incidents, mais moins pour les annonces de nouveautés (perte d’information).
