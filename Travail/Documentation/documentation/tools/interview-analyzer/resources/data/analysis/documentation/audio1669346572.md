## 2️⃣ CR détaillé des échanges  

### 2.1 Présentation de l’interviewé  
* **Rôle** : développeur·se front & back, équipe « filière enquête », module Sabian (outils de collecte).  
* **Expérience** : 7‑8 ans de dev, précédemment sur la statistique.  
* **Missions quotidiennes** : développement de fonctionnalités mutualisées, suivi de production, assistance aux utilisateurs, participation aux déploiements.  

### 2.2 Pratiques de code & outils  
| **Aspect** | **Ce qui a été dit** |
|------------|----------------------|
| **Langages / frameworks** | Java Spring (Spring Boot récent), JavaScript (Node/React). |
| **IDE** | IntelliJ pour Java, VS Code (avec extension *ProGeek*) pour JavaScript. |
| **Déploiements** | Fréquence variable : API questionnaire & front ≈ 1 déploiement/mois (ou plus), API critiques ≈ 2‑3 déploiements/an + hot‑fixes. |
| **Micro‑services** | Complexité due aux dépendances multi‑modules ; besoin d’attendre la validation de tous les modules avant de pousser. |
| **Gestion d’incidents** | Alertes par mail, sons de déploiement, suivi via canal métier dédié, rotation des personnes en charge du suivi des pods. Analyse des logs, requêtes DB, revue de code, assistance via Zoom. |
| **Observabilité** | Dashboard maison affichant versions, métriques CVE, alertes. Pas d’intégration directe dans les IHM des applis. |
| **Outils de prod** | Renet (création VM), Rundeck (jobs d’automatisation), Majiba (API), observabilité (alerting, logs). |
| **Problèmes rencontrés** | • Création VM lourde.<br>• Documentation fragmentée.<br>• Manque d’automatisation de l’alerting.<br>• Difficulté à gérer le multi‑navigateur (offline). |
| **Support / assistance** | Référents identifiés (Eric, Michael). Assistance ponctuelle via tickets, canaux internes. |

### 2.3 Points de friction autour des catalogues de services  
* **Dispersion** : services accessibles via GitLab, URL directes, DPII Planet, etc. → perte de temps pour les retrouver.  
* **Ergonomie** : aucune interface unifiée, chaque service a son propre look & feel.  
* **Documentation** : souvent “one‑shot”, pas de versionning centralisé, difficile de savoir quelles versions sont en fin de vie.  
* **Processus de création / mise à jour** : dépendance forte à l’équipe Ops (R.I.A.P), pas de self‑service.  

### 2.4 Besoins exprimés (sans préconisation)  
1. **Centralisation** d’une documentation unique (catalogue, IHM, procédures).  
2. **Simplification** du workflow de création de VM / plateformes (interface plus rapide, visibilité sur le statut).  
3. **Intégration** de l’observabilité dans les IHM applicatives (accès direct aux logs, métriques, historique).  
4. **Réduction du bruit** d’alertes (filtrage, priorisation).  
5. **Support multi‑navigateur** pour les applications offline (synchronisation du stockage local).  
6. **Clarté des road‑maps** (dates de fin de service, migrations, évolutions de stack).  

### 2.5 Autres remarques / anecdotes utiles  
* **Migration vers Kube** : processus bien accompagné par l’équipe questionnaire, mais la migration de « Cymbul » reste à venir.  
* **Micro‑frontend** : problème de CSP/HTSTS, solution envisagée mais coûteuse.  
* **Formation** : besoin d’une documentation « self‑service » plus simple pour monter en compétence rapidement.  
* **Communication** : les annonces d’évolution (ex. nouveau navigateur, fin de service) sont parfois diffusées tardivement, rendant la transition difficile.  
* **Culture DevOps** : l’interviewé se sent parfois « débordé » par la double casquette développeur + opérateur, même si la philosophie U‑Build‑it, U‑Run‑it est partiellement adoptée.

## 3️⃣ Autres éléments (hors recommandations)  

* **Outils de CI/CD** : deux pipelines distinctes (branch “profiteur” vs “débat”) avec templates partagés, mais la visibilité sur les *values* injectées reste limitée.  
* **Gestion des secrets** : token Majiba géré manuellement, perçu comme lourd.  
* **Gestion des logs** : parfois nécessité de sacrifier des logs anciens pour libérer de l’espace, sans procédure claire.  
* **Gestion des dépendances** : migration Spring 4 → Spring 5 en cours, mais les dates de fin de support ne sont pas centralisées.  
* **Ressources humaines** : un « DevOps champion » (Eric) porte une grande partie de la charge d’automatisation, créant un point de friction lorsqu’il n’est pas disponible.  
* **Environnement de travail** : le développeur travaille majoritairement en remote, dépend d’un canal métier dédié pour les incidents, et d’un canal interne (chat) pour la veille technique.
