## 3️⃣ Irritants & points de friction  

| Domaine | Problèmes relevés |
|---------|-------------------|
| **Temps de déploiement** | Pipelines longs : création d’image → push → Majiba → déploiement (30 min à 2 h selon le module). Conflits lorsqu’un module (ex. BAC) met plus de temps que les autres. |
| **Multiplicité d’outils** | Beaucoup d’outils différents (Sonar, SOS, KubeApp, Majiba, etc.) → surcharge cognitive, difficulté à savoir lequel utiliser. |
| **Communication / support** | Tchap jugé « chiant » (notifications manquées, télétravail). Ticketing Siamois perçu comme lent (ex. ticket resté 2 semaines). Pas de visibilité claire sur le propriétaire du problème (réseau, DB, etc.). |
| **Documentation** | Documentation existante mais parfois difficile à localiser ou à comprendre pour un·e junior. |
| **Visibilité des contacts** | Quand un incident survient, le développeur ne sait pas toujours qui contacter (prod, réseau, DB, etc.). |
| **Formation / montée en compétences** | Formation interne disponible mais limitée : besoin d’accompagnement sur de nombreux outils (ex. Kube, SOS). |
| **Gestion des environnements** | Création d’un nouvel environnement (DV) nécessite de connaître les jobs Rundeck ou de solliciter d’autres équipes, pas de self‑service. |
| **Gestion des incidents** | Analyse de premier niveau souvent à la charge du développeur ; si le problème dépasse ses compétences, il faut escalader, mais le processus d’escalade n’est pas toujours clair. |

## 4️⃣ Besoins exprimés (ou implicites)  

| Besoin | Détails |
|--------|---------|
| **Self‑service pour les environnements** | Possibilité de créer / cloner des environnements (DV, pré‑prod) via une interface simple, sans devoir passer par un ticket ou un collègue. |
| **Pipeline plus rapide** | Optimisation du temps de build / déploiement (ex. caching, parallélisation, réduction des étapes manuelles). |
| **Centralisation de la connaissance** | Un hub (wiki, catalogue) listant : <br>• Outils disponibles et leur usage <br>• Procédures d’incident (qui contacter, comment). |
| **Réduction du nombre d’outils** | Regrouper les fonctions similaires (ex. analyse de code, CVE) dans une plateforme unique ou un tableau de bord. |
| **Meilleure visibilité des contacts** | Annuaire clair des experts (ex. Rundeck, DB, réseau) avec leurs domaines d’expertise. |
| **Formation ciblée** | Sessions courtes sur les outils les plus critiques (Majiba, KubeApp, SOS) et sur les bonnes pratiques CI/CD. |
| **Amélioration du suivi des tickets** | Système de suivi plus transparent (statut, SLA) pour éviter les « bouteilles d’attente ». |
| **Support de l’onboarding** | Mentorat ou binôme systématique pour les nouvelles tâches (ex. pipeline, restauration DB). |
| **Feedback en temps réel** | Dashboard de santé de la prod (alertes, logs) accessible directement depuis l’IDE ou le navigateur. |

## 5️⃣ Insights clés pour le **Platform‑Engineering**  

| Insight | Implication pour la plateforme |
|--------|--------------------------------|
| **Le développeur veut être autonome** | Fournir des **self‑service** (provisioning d’environnements, déclenchement de jobs) afin de réduire les dépendances aux équipes ops. |
| **Temps de cycle CI/CD est un frein** | Prioriser l’**optimisation des pipelines** (caching, parallélisation, artefacts pré‑construits) et exposer les métriques de durée. |
| **Fragmentation des outils crée de la friction** | Concevoir une **interface unifiée** (dashboard) qui agrège les fonctions de Sonar, SOS, Majiba, etc., ou au moins un **catalogue** centralisé. |
| **Manque de visibilité sur les contacts** | Intégrer un **annuaire d’expertise** dans la plateforme (qui gère Rundeck, DB, réseau, etc.) avec recherche rapide. |
| **Documentation et onboarding sont critiques** | Créer un **knowledge‑base** structuré, versionné, avec des guides pas‑à‑pas (ex. déploiement d’un module, création d’un DV). |
| **Communication asynchrone peu fiable** | Proposer un **système de tickets intégré** à la plateforme, avec suivi en temps réel et notifications ciblées. |
| **Le développeur porte la responsabilité du run** | Mettre à disposition des **outils de monitoring** simples (dashboards, alertes) directement liés aux pipelines, pour que le dev puisse diagnostiquer rapidement. |
| **Formation continue souhaitée** | Intégrer des **micro‑formations** (vidéos, labs) directement dans la plateforme, accessibles depuis le tableau de bord. |
| **Le besoin d’une vue globale sur les artefacts** | Centraliser les **artefacts (Docker images, JAR, etc.)** dans un registre unique avec recherche et métadonnées (version, environnement cible). |
| **Le sentiment d’être “bloqué” sur les incidents** | Implémenter un **assistant de résolution** (ex. suggestions de solutions basées sur historiques d’incidents). |

## 6️⃣ Autres éléments pertinents  

* **Culture DevOps** : le développeur comprend le principe « you build it, you run it », mais ressent le poids de la partie opérationnelle (déploiement, monitoring) sans toujours disposer des moyens adéquats.  
* **Évolution de carrière** : le participant envisage de rester développeur mais souhaite consolider ses compétences (Java, CI/CD, sécurité). Une plateforme qui facilite la montée en compétences pourrait améliorer la rétention.  
* **Environnement matériel** : les renouvellements de postes (ordinateurs) entraînent des pertes de configuration et de temps d’installation d’outils, point à prendre en compte pour le **onboarding**.  
* **Feedback positif** : la machine à café et la communication intra‑équipe sont perçus comme des points forts – la plateforme ne doit pas nuire à ces aspects humains.
