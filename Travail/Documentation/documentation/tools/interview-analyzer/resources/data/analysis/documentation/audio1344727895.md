## 2. CR des échanges – Résumé détaillé de l’interview  

### 2.1 Contexte & rôle de l’interviewé  
- Responsable d’un groupe de maintenance (6 personnes) ; gère 3 applications : deux en fin de vie, une modernisée (Spring Boot + React).  
- Travail sur la migration d’applications legacy vers des standards modernes, avec un fort accent sur la qualité du code et les tests.  

### 2.2 Points forts de l’environnement actuel  
- **Autonomie** : les équipes n’attendent plus de “plateforme” pendant des années ; elles peuvent créer leurs propres pipelines.  
- **Qualité** : adoption de Spring Boot, rationalisation des dépendances, couverture de tests élevée ; le “craft” (bonnes pratiques DevOps) est perçu comme un vrai atout.  
- **Dashboard maison** : agrège logs, batchs, alertes ; permet de détecter rapidement les incidents et de les traiter sans perte de temps.  
- **Support réactif** : les équipes de support (ex. : libéa) sont perçues comme très aidantes lorsqu’on les sollicite.  

### 2.3 Principaux irritants / problèmes rencontrés  

| **Thème** | **Exemple d’irritant** |
|-----------|------------------------|
| **Performance des outils** | Majiba : livraison d’un livrable qui prend 30 min à 1 h, alors qu’en manuel cela ne prend que 5 min. |
| **Hétérogénéité des plateformes** | Multiples accès (GitLab, URL directes, DPII Planet, Run‑Deck, etc.) → perte de temps à comprendre chaque outil. |
| **Transfert de tâches Ops** | Micro‑segmentation, tags, changements d’infrastructure imposés aux devs sans moyens supplémentaires. |
| **Communication fragmentée** | 15 canaux de chat différents, annonces d’incidents tardives (ex. : expiration de mots‑de‑passe annoncée le jour même). |
| **Services transverses peu fiables** | Spock, Gravity, etc. : pas de logs, besoin de “bombarder” l’API jusqu’à obtenir un code retour, absence de suivi d’état. |
| **Manque de visibilité globale** | Aucun calendrier partagé pour les évolutions des services, chaque équipe travaille sur son propre planning. |
| **Outils obsolètes / migrations non annoncées** | Passage de Minio à une console sans préavis, impact sur les équipes qui doivent ré‑adapter leurs scripts. |
| **Charge de travail supplémentaire** | Recherche d’informations dans 50 sources différentes, impossibilité de suivre les évolutions de tous les services. |
| **Documentation insuffisante** | Absence de page centrale listant tous les services utilisés, leurs versions, leurs SLA. |

### 2.4 Processus de déploiement & cycle de vie  

1. **Création d’un environnement**  
   - Sur Kubernetes (Kube) : demande de namespace, puis configuration via YAML (peut être lourde).  
   - Sur VM : utilisation de Run‑Deck, jobs manuels.  
   - L’interviewé estime que la mise en place initiale prend **une demi‑journée** au maximum, mais cela dépend du type d’environnement.  

2. **Pipeline CI/CD**  
   - Pipelines automatisés pour les nouvelles applis : déploiement en 5 min, tests unitaires et d’intégration.  
   - Pipelines legacy (Majiba) restent lents et parfois manuels.  

3. **Gestion des incidents**  
   - Dashboard maison → alertes quotidiennes (CVA critiques traitées immédiatement, majeures planifiées).  
   - Si le service transverse ne fonctionne pas, il faut ouvrir un ticket ; aucune solution de repli.  

4. **Montée de version**  
   - Sur les nouvelles applis, la couverture de tests (≈ 75 %) permet de monter de version en toute confiance.  
   - Sur les legacy, il faut analyser les batchs impactés, souvent sans spécifications ni tests, ce qui rend la montée de version risquée.  

### 2.5 Besoins exprimés  

| **Besoins fonctionnels** | **Besoins organisationnels** |
|---------------------------|------------------------------|
| • Templates CI/CD prêts à l’emploi (ex. : Java + Kube) avec variables à remplir. | • Point de contact unique (ou “chef d’orchestre”) pour centraliser les informations sur les services transverses. |
| • Visibilité sur la cause de la lenteur des pipelines (logs, métriques). | • Calendrier partagé des évolutions et des maintenances des services (ex. : micro‑segmentation, tags). |
| • Documentation centralisée listant tous les services, leurs versions, leurs SLA. | • Processus de concertation avant toute modification d’un service transversal. |
| • Outils homogènes (interface unique, même mode d’accès). | • Réduction du nombre de canaux de communication (un canal global ou un hub d’information). |
| • Automatisation des changements d’infrastructure (ex. : tags, micro‑segmentation). | • Ressources supplémentaires pour les tâches Ops transférées aux devs. |

### 2.6 Points de vigilance supplémentaires (non‑exhaustifs)  

- **Confiance** : lorsqu’un service transverse échoue, l’interviewé perd confiance et préfère développer une solution maison.  
- **Charge cognitive** : la multiplicité des outils et des canaux augmente la charge mentale des développeurs, qui sont déjà très occupés par leurs US.  
- **Évolution des outils** : les migrations d’outils (ex. : Minio → console) sont perçues comme des “chocs” qui perturbent la productivité.  
- **Culture DevOps** : la transition vers une vraie culture DevOps est en cours, mais le manque d’automatisation de certaines tâches Ops freine l’adoption.

## 3. Autres éléments recueillis (sans préconisations)

- **Historique de la plateforme** : les premiers services (ex. : FTP, scripts maison) ont été remplacés progressivement, mais les traces restent dans les processus.  
- **Rôle du “Craft”** : perçu comme un levier d’amélioration continue, mais nécessite un soutien organisationnel (temps, ressources).  
- **Impact des dépendances externes** : la dépendance à des outils propriétaires (ex. : Majiba) crée des blocages lorsqu’ils sont mis à jour ou retirés.  
- **Gestion des licences** : certaines équipes utilisent des IDE ou des outils IA (ex. : Mistral) qui nécessitent des licences, ce qui complique l’uniformisation.  
- **Formation & montée en compétence** : les nouveaux devops (ex. : jeune développeur du groupe) ont besoin d’un accompagnement sur les aspects DevOps, ce qui renforce l’importance d’une documentation claire et d’un point de contact unique.
