## 2. CR détaillé des échanges  

### 2.1 Présentation du participant  
* **Parcours** : arrivé à l’INSEE en septembre 2024, issu d’un Master Statistique (ENSAI).  
* **Rôle actuel** : développeur back‑end (Java / Spring Boot) en renfort de l’équipe back, travaille sur des API de nomenclature et questionnaire.  
* **Ancienneté** : 1 an + 6 mois dans l’équipe, a déjà évolué d’analyste‑développeur à développeur confirmé.  

### 2.2 Outils et pratiques quotidiennes  

| **Activité** | **Outils** | **Description** |
|--------------|------------|-----------------|
| **Développement** | IntelliJ, GitHub Desktop, Git Bash | Branches de feature, PRs, revue de code. |
| **CI/CD** | GitLab (pipelines YAML), Argo CD, Zodorz (gestion de versions) | Déploiement en recette/DV via *snapshot* + label, mise à jour du fichier YAML pour changer la version. |
| **Gestion des versions** | GitLab, Argo CD | Labels et snapshots automatisés, suivi des versions en DVQF et prod. |
| **Gestion des bases** | Beavers (outil interne) | Création et maintenance de bases de données. |
| **Documentation** | Docs internes (non centralisées), guides ponctuels | Consultation ponctuelle (ex. : doc Argo CD, guide Volta). |
| **Communication** | Daily 9 h30, salons Slack transverses, réunions Litech | Partage d’avancement, revue de PR, suivi des incidents. |
| **Support** | Lead tech (Laurent), senior dev (Nico) | Aide sur nouveaux outils, résolution de problèmes (ex. : récupération de tokens, configuration de pipelines). |

### 2.3 Points forts relevés  

* **Pipeline fiable** : le processus de build → image → déploiement fonctionne sans friction majeure.  
* **Automatisation** : les règles de merge, les scans de sécurité et de couverture sont déjà en place.  
* **Culture du partage** : les développeurs s’entraident sur les PR et les revues de code.  
* **Réactivité en urgence** : possibilité de déployer directement depuis l’APR lorsqu’une fonctionnalité doit être testée rapidement.  

### 2.4 Irritants & zones d’ombre  

| **Thème** | **Exemple d’irritant** |
|-----------|------------------------|
| **Multiplicité des plateformes** | Coexistence de GitHub (historique) et GitLab (nouveaux projets) → confusion sur où pousser les changements. |
| **Vocabulaire & concepts** | Termes comme « snapshot », « label », « image d’hocs » sont incompris par les nouveaux arrivants. |
| **Documentation** | Pas de référentiel unique ; les dossiers Git contiennent parfois des docs obsolètes ou mal nommés. |
| **Autonomie sur les pipelines** | Le développeur ne touche pas aux pipelines (composant VSN DIL) ; toute modification passe par le lead tech. |
| **Visibilité des environnements** | Chaque équipe possède son propre environnement, mais il n’existe pas de vue d’ensemble (qui utilise quoi, quelles versions). |
| **Communication transversale** | Les informations majeures (ex. : migration Kube DMZ) sont communiquées de façon ponctuelle, difficile à suivre. |
| **Formation / onboarding** | Pas de parcours structuré pour le *platform engineering* ; apprentissage « au fil de l’eau » avec l’aide de seniors. |
| **Gestion des incidents** | Les devs ne sont pas directement impliqués dans le run / debug ; ils passent par un intermédiaire (Litech) qui relaie les alertes. |

### 2.5 Besoins exprimés  

1. **Centralisation de la documentation** – un hub unique contenant glossaire, guides CI/CD, procédures de déploiement, et références aux environnements.  
2. **Uniformisation des plateformes** – migration complète vers GitLab (ou GitHub) afin d’éliminer le double suivi.  
3. **Visibilité globale des environnements** – tableau ou dashboard listant les services, leurs versions, les environnements associés.  
4. **Autonomie sur les pipelines** – pouvoir modifier ou créer des pipelines simples sans passer systématiquement par le lead tech.  
5. **Formation ciblée** – ateliers GitOps, sécurité CI/CD, observabilité, pour réduire la courbe d’apprentissage.  
6. **Meilleure diffusion de l’information** – canal dédié (ex. : newsletter interne, espace Confluence) pour les évolutions majeures (migrations, nouvelles pratiques).  

### 2.6 Points d’éclaircissement supplémentaires  

* Le participant ne travaille jamais directement avec les équipes prod ; il ne possède pas les accès ni les outils de monitoring (ex. : alertes K8s).  
* Il a déjà été impliqué dans la mise en place d’un système de rotation (tournante) pour la gestion des incidents, mais il ne l’utilise que ponctuellement.  
* Il a exprimé le souhait d’un « router » ou d’un tableau de bord qui relie le recettage à la mise en production, afin de se sentir plus légitime dans le processus de déploiement.

## 3. Autres éléments (sans préconisations)

* **Culture DevOps vs DevSecOps** – le participant comprend la différence (sécurité intégrée) mais ne voit pas encore de pratique DevSecOps concrète dans son quotidien.  
* **Gestion des conflits de version** – les pipelines imposent des règles strictes (ex. : pas de merge si la CVE ne passe pas) ; cela est perçu comme protecteur mais parfois trop restrictif.  
* **Outils de messagerie** – les notifications GitHub (pull‑request, mentions) sont le principal canal d’alerte ; aucune utilisation d’outils de messagerie dédiés (ex. : Slack / Mattermost) pour le monitoring.  
* **Sentiment d’appartenance** – le développeur se sent « bien intégré » dans son équipe, mais reste en marge des décisions transverses (ex. : roadmap plateforme).
